# dbt-core 1.9.x/dbt-common<1.29 pin protobuf<6.0, which forces the
# resolver onto dbt-common<=1.28.0, whose own deepdiff<8.0,>=7.0 constraint
# leaves the vulnerable deepdiff==7.0.1 installed (CVE-2025-58367 CRITICAL,
# CVE-2026-33155 HIGH; fixed in 8.6.1/8.6.2 respectively). dbt-core 1.11.x
# raises the protobuf ceiling to <7.0 and requires dbt-common>=1.37.3, whose
# deepdiff<9.0,>=7.0 constraint lets pip resolve a patched deepdiff. Bump
# both dbt-core and dbt-postgres together (no compatible dbt-common exists
# that relaxes deepdiff without also raising the protobuf floor).
# dbt-core 1.12.3 widens the sqlparse constraint to >=0.5.5,<0.7.0, allowing
# pip to resolve sqlparse 0.6.0 (fixed for CVE-2026-54284, CVE-2026-59893,
# CVE-2026-59894, CVE-2026-71491). Pin sqlparse>=0.6.0 explicitly to ensure
# the patched version is always installed.
dbt-core==1.12.3
dbt-postgres==1.11.0
# dbt-duckdb declares dbt-core>=1.8.0 (loose floor, no upper pin as of
# 1.11.0), so it resolves cleanly alongside the dbt-core==1.12.3 pin above
# without forcing any of the protobuf/deepdiff/sqlparse constraints noted
# above to move. Pinned to the same 1.11.0 minor as dbt-postgres above,
# rather than dbt-core's 1.12.3, because neither adapter has published a
# 1.12.x release yet (checked against PyPI); Renovate will pick up a
# matching bump once one ships. images/dbt/Dockerfile's builder stage
# import-checks both adapters against the pinned dbt-core after install, so
# a resolver-satisfiable but runtime-broken combination fails the image
# build (and CI) instead of only surfacing in a running container.
dbt-duckdb==1.11.0
deepdiff>=8.6.2
sqlparse>=0.6.0
