# CDS Production Threat Model and Penetration-Test Plan

Version: 1.0
Status: Draft — reviewed by maintainers before controls in issues #205, #206, #207, #210, #211, and #216 are implemented against it.
Related: [#212](https://github.com/RonaldHensbergen/composable-data-stack/issues/212) (this document), [#64](https://github.com/RonaldHensbergen/composable-data-stack/issues/64) (production-readiness epic).

## 1. Purpose and scope

This document defines the assets, trust boundaries, attacker capabilities, and
prioritized risks for a CDS-rendered production deployment, and derives a
repeatable penetration-test plan from that model. It exists to give the
remaining production-hardening issues (#205, #206, #207, #210, #211, #216) a
shared, testable set of threats to design controls against, rather than each
issue inventing its own threat assumptions.

**In scope:**

- The CDS CLI itself (`validate` / `plan` / `render` / `test` / `security` /
  `up`, and non-exhaustively also `diff`, `state`, `preflight`, `init`,
  `list`, `use`, `completion`) and the artifacts it produces (rendered
  Compose files, plans, diagnostics). `diff` and `state` also touch the
  secret boundary (Boundary D) the same way `plan`/`validate` do.
- Modules shipped in `modules/` (currently Postgres, Superset, KeyDB, Dagster,
  Vault, and any added afterward) and their generated runtime configuration.
  This model is expressed in terms of module **categories** (warehouse,
  BI, cache, orchestration, secrets, and future categories such as
  transformation or quality) rather than fixed module names, so it remains
  valid as new modules are added without requiring a rewrite.
- Profiles and environment overlays (`profiles/**/profile.yaml`,
  `profiles/**/environments/*.yaml`) and the secret-resolution path
  (`cli/secrets.py`, `${CDS_*}` placeholders).
- CI/CD supply chain for CDS-published images (`.github/workflows/publish-images.yml`,
  `.github/workflows/image-security-scan.yml`), including signing/provenance
  (`cli/image_verification.py`).
- The Docker host and daemon underneath a rendered stack, to the extent CDS
  can inspect or influence it (rootless mode, socket exposure, capabilities).

**Out of scope (tracked separately):**

- Kubernetes-specific attack surface — tracked under #65 and does not block
  the Docker Compose production baseline.
- Vulnerabilities in third-party module images themselves (Postgres, Superset,
  Dagster upstream code) beyond CDS's ability to pin, scan, and verify them.
- Physical/cloud-provider infrastructure security outside the host running
  Docker.

The diagram labels boundary A (the `dockerDaemon` subgraph), boundary B (the
`moduleA`↔`moduleB` contract-mediated edge inside it), boundary C (the
registry-pull edge into boundary A), and boundary D (the `envFile` →
`dockerCompose` edge, labeled "trust boundary D") — the four named boundaries
below correspond one-to-one with these diagram elements.

Each profile composes an arbitrary, interchangeable set of module instances
(warehouse, BI, cache, orchestration, secrets, and any future category); the
diagram deliberately does not name specific modules or a fixed number of
them. `moduleA`/`moduleB`/`moduleN` represent any two connected instances and
"any remaining instances a profile declares," not a fixed 1:1:1 topology.
The only sanctioned way one module instance reaches another is through a
`consumes`/`provides` contract binding — there is no unqualified service mesh
between all instances in a profile, which is itself a tracked gap (see T9 in
§5.2). A secrets module (e.g. Vault) is one such instance like any other; it
has no special standing in this diagram beyond being optional in a given
profile.

Named boundaries used throughout this document:

- **Boundary A — CLI/host boundary.** Between the machine running `cds` (an
  operator laptop or a CI runner) and the Docker daemon it drives. CDS itself
  never talks to the daemon directly (`cds up` shells out to `docker
  compose`), so this boundary is crossed once per `docker compose` invocation.
- **Boundary B — inter-service network boundary.** Between containers on the
  Compose-rendered network. Contracts (`consumes`/`provides`) are the only
  sanctioned way one module's service reaches another's.

  **Target production model (gap tracked as T9, owned by #70/#205/#207).**
  Today every profile renders one flat network regardless of module mix, so
  this boundary exists only in principle. A general production topology —
  applicable to any combination of interchangeable modules, not a fixed set —
  should instead partition module instances into at least three tiers,
  independent of which module fills each role:

  1. **Edge tier.** Instances that terminate operator- or public-facing
     traffic (e.g. whichever module provides the profile's BI/admin UI or
     external API). Only this tier may be reachable from outside Boundary A.
  2. **Application/orchestration tier.** Instances that coordinate work and
     call into the data tier on the edge tier's behalf (e.g. whichever module
     provides orchestration or business logic). Reachable from the edge tier,
     not directly from outside Boundary A.
  3. **Data tier.** Instances holding persisted state (e.g. whichever modules
     provide warehouse or cache contracts). Reachable only from the
     application/orchestration tier that legitimately consumes their
     contracts — never directly from the edge tier or from outside
     Boundary A.

  A secrets-providing module (e.g. Vault) sits alongside, not inside, these
  tiers: any tier may reach it to resolve a secret reference, but it must
  never be reachable from outside Boundary A. Tier membership is derived from
  a module's declared contracts (what it `provides`/`consumes`), not from a
  hardcoded module name, so this model holds as new module categories are
  added. Network policy should deny cross-tier and cross-module traffic by
  default and allow only the specific `consumes`/`provides` bindings a
  profile actually declares — equivalent to a default-deny stance with
  contract bindings as the allowlist.
- **Boundary C — registry/supply-chain boundary.** Between the CI pipeline
  that builds/signs/publishes CDS images and the host that later pulls and
  verifies them via `cli/image_verification.py`.
- **Boundary D — secret boundary.** Between the operator's secret store
  (`.env`, environment, or a secrets module like Vault) and everything CDS
  ever writes to disk or stdout. The actual control here is the
  placeholder-rendering code path itself (`cli/renderer.py` `_resolve_expr`,
  which emits `${CDS_*}` and never a resolved value) plus its regression
  tests; `CDS-SEC-006`, `CDS-SEC-030`, and `CDS-SEC-071` describe the intended
  policy but are not evaluated (`scope: ["none"]`, and `030`/`071` are also
  `enabled: false`), so the rule engine skips them entirely (`cli/security.py`
  scope filtering) rather than actively enforcing this boundary.

## 4. Threat actors

| Actor | Capability | Motivation |
| --- | --- | --- |
| **External network attacker** | No credentials; can reach any port the host exposes to a routable network | Data theft, ransomware, botnet recruitment |
| **Malicious/compromised dependency** | Can execute code inside a build or at runtime inside one container (e.g. compromised base image, malicious PyPI package pulled at container build time) | Supply-chain compromise, lateral movement |
| **Malicious/compromised CI job** | Can execute arbitrary code with the CI runner's permissions, including the `GITHUB_TOKEN` and OIDC token used for keyless signing | Publish a tampered/backdoored image under a trusted identity |
| **Insider with repo write access** | Can modify profile/module YAML, `rule-set.json`, or CI workflow files | Weaken security policy, exfiltrate secrets, plant malicious module config |
| **Compromised operator workstation/laptop** | Has the operator's `.env`/environment secrets and can run `cds`/`docker` locally | Direct access to all resolved secrets and local Docker socket |
| **Malicious/misconfigured co-tenant on shared host** | Runs another workload on the same Docker host/daemon | Container escape, resource exhaustion, socket abuse |
| **Curious/careless operator** | Legitimate access; may misconfigure a production profile (e.g. picks `local` overlay for a public deployment) | Unintentional exposure, not malicious but treated as a risk source |

## 6. Risk prioritization summary

Ranked by (likelihood × impact), highest first, mapped to the owning
follow-up issue:

1. **T5 / T9 / T10 / T16 / T26 / T27** — no authentication enforcement, no
   network segmentation, no TLS, non-rootless daemon exposure, and no
   backup/restore path are the highest-impact gaps because each allows a
   single compromised or misconfigured service to fully compromise
   confidentiality or availability of the whole stack. Owners: #206, #70,
   #205, #211, #210.
2. **T3 / T4** — dead/buggy security rules (`CDS-SEC-070` never fires,
   `CDS-SEC-010`'s first branch is dead code) give false confidence that
   credential-leak and default-credential classes are caught when they are
   not. Owner: #206 (plus the standalone bug issues #297, #292).
3. **T15 / T18** — missing runtime confinement and production process
   managers increase the blast radius of a successful application-layer
   compromise but require an existing compromise to matter. Owners: #207,
   #216.
4. **T23** — no continuous rescanning means a newly disclosed CVE in an
   already-running image goes undetected indefinitely. Owner: #209.
5. **T17** — host hardening baseline is undocumented; mitigated somewhat by
   T16's rootless requirement once implemented. Owner: #211.
6. **T22a** — the signed-images fixture is trusted as-is with no independent
   check, so any repo-write insider can mark a backdoored image as signed
   and bypass image verification entirely. Owner: unassigned; flag for
   #209/#211.

## 7. Penetration-test plan

### 7.1 Scope and rules of engagement

- **Target:** a rendered instance of the production-hardened reference
  profile once #70 lands (or, until then, the closest available
  production-classified profile), deployed to an isolated test host that is
  not shared with any other workload.
- **Out of bounds:** the CDS CLI's own host machine/CI infrastructure,
  third-party SaaS registries (ghcr.io/Docker Hub) beyond read-only
  reconnaissance, and any production data — testing uses synthetic
  data only.
- **Duration/cadence:** run once ahead of the first tagged production
  release, then on every subsequent minor release that touches a control in
  §5, and at minimum annually thereafter.
- **Authorization:** requires written sign-off from the repository owner
  before any active (non-read-only) testing begins, since some tests
  (credential brute-force, DoS) can degrade service availability.

### 7.2 Test phases

1. **Reconnaissance (passive).** Enumerate exposed ports/services from
   outside Boundary A and Boundary B; diff against the profile's declared
   `ports`/`expose` entries to catch any undeclared exposure (validates T8,
   T9).
2. **Secrets and configuration review.** Inspect `docker inspect`, container
   environment, and process list for resolved secrets in command args or
   env vars (validates T2, T3); attempt to read `.env`/config file
   permissions from a non-privileged account on the host (validates T17).
3. **Authentication and authorization testing.** Attempt unauthenticated
   connections to the warehouse, cache, and BI admin UI; attempt default/weak
   credential logins (validates T4, T5, T8).
4. **Network segmentation testing.** From within a low-privilege service
   container (e.g. cache), attempt to reach the warehouse and orchestration
   services directly, bypassing declared contracts (validates T9).
5. **Transport security testing.** Capture traffic on Boundary B (e.g. via a
   test-only network tap) to confirm credentials/tokens are not sent in
   plaintext where TLS is expected (validates T10).
6. **Container escape and privilege testing.** From inside each container,
   attempt privilege escalation, capability abuse, and host filesystem/socket
   access consistent with its declared confinement profile (validates T12,
   T13, T14, T15, T16).
7. **Supply-chain verification testing.** Attempt to deploy a tampered image
   with a forged tag/digest and confirm `cds security --verify-images`
   rejects it; confirm a `latest`/unpinned tag is flagged before reaching
   this phase (validates T19–T22, T22a, T24).
8. **Backup/restore drill.** Trigger a full data-loss simulation (destroy the
   warehouse volume) and time the restore against the RPO/RTO targets defined
   once #210 lands (validates T26, T27).
9. **Reporting.** Every finding is recorded with severity (aligned to the
   `high`/`medium`/`low` vocabulary already used by `rule-set.json`), owner,
   remediation deadline, and a retest date; findings are filed as GitHub
   issues linked back to this document and to the owning production-readiness
   issue from §5.

### 7.3 Tooling boundaries

- Network/service testing: standard open-source tools (e.g. `nmap`, `curl`,
  a TLS inspection tool) run from a test-only network segment.
- Container/runtime testing: `docker inspect`, `docker exec`, and
  container-escape test suites run only inside the isolated test host — never
  against a shared or production host.
- Supply-chain testing: reuses CDS's own `cds security --verify-images` and
  `cosign` tooling as the primary detection surface, plus manual crafting of
  a deliberately non-compliant image/fixture — including tampering with
  `tests/fixtures/signed-images.json` itself (e.g. marking a bad digest as
  `"signed": true`, per T22a) as well as crafting fake unsigned images — to
  confirm fail-closed behavior (mirrors the existing regression-test pattern
  in `tests/test_image_verification.py`).
- No fuzzing or DoS testing against any shared CI or registry infrastructure.

## 8. Findings tracking

Findings from any penetration test or from this document's own review must
be filed as GitHub issues using this template and linked from this section
once opened:

| Field | Description |
| --- | --- |
| Severity | `high` / `medium` / `low`, matching the vocabulary in `cli/resources/rule-set.json` |
| Owner | GitHub handle responsible for remediation |
| Remediation deadline | Target date, scaled to severity (e.g. high: 30 days, medium: 90 days, low: next minor release) |
| Retest status | `not started` / `scheduled` / `passed` / `failed`, updated after each retest |
